# node_alive_monitoring

Symbol の API ノード / Peer ノードを **GitHub Actions だけ**で死活監視し、異常を Discord / Slack に通知する。
サーバーもデータベースも不要で、運用コストはゼロ。

- 外部ライブラリ依存ゼロ（Node.js 標準ライブラリのみ、`npm install` 不要）
- 10 分ごとに自動実行（ただし GitHub の都合で大幅に遅れる。後述）、落ちたら通知、復旧しても通知
- 瞬断では鳴らない（2 回連続の失敗で初めて通知）
- **監視システム自体が止まったことに気づける**仕組み付き

## 仕組み

10 分ごとに cron で Node.js スクリプトを 1 回実行する。
実行間の状態（前回のチェーン高、連続失敗回数、通知済みフラグ）は
`monitoring-state` ブランチの `state.json` に force push して引き継ぐ。

```
[cron 10分] → checkout → state.json を取得
                            ↓
                   全ノードを並列に検査
                            ↓
          前回の state と突き合わせて「通知すべきこと」を判定
                            ↓
                  Discord / Slack へ送信
                            ↓
          state.json を monitoring-state へ force push
```

> **この force push を「変更があったときだけ」に最適化してはいけない。**
> GitHub は Public リポジトリの scheduled workflow を、リポジトリ活動が 60 日間
> 途切れると自動で無効化する。毎回の push がその活動そのものであり、条件付きに
> した瞬間、監視は 2 か月後に自分で止まる。しかも止まったことは通知されない。

> **`state.json` を main ブランチにコミットしてはいけない**（`.gitignore` 済み）。
> ワークフローの `Restore state` ステップは、state ブランチに一時的に到達できないときは
> 推測せず中断する。これが安全なのは、チェックアウトした作業ディレクトリに `state.json` が
> 存在しない前提があるからに限る。もしコミットされていたら、中断後も `Persist state` は
> `if: always()` でそのまま走り、古い（コミットされた）`state.json` を force push して
> 本当の state を上書きしてしまう。

## 監視内容

| 対象 | 確認すること |
|---|---|
| API (http / https) | `/node/health` が `apiNode` と `db` の両方で `up` を返すか |
| API (http / https) | `/chain/info` の `height` が前回より進んでいるか |
| Peer | Peer ポート（既定 7900、`peer.port` で変更可）への TCP 接続が確立するか |

2 回連続で失敗したときに初めて通知する（瞬断による誤報を防ぐため、実質 20 分以上継続した障害が対象）。
障害が続いている間は再通知しない。復旧したら復旧通知を送る。

> **実際の検知は数時間遅れることがある。** GitHub は無料枠の scheduled workflow を
> 指定どおりには発火しない。[制限事項](#制限事項)に実測値を載せてあるので、
> 導入前に必ず目を通すこと。分単位の検知が必要な用途にはこの仕組みは向かない。

チェーン高を見ているのは、**プロセスは生きているが同期が止まっている**状態を捕まえるため。
Symbol は約 30 秒で 1 ブロックなので、10 分あれば 20 ブロック前後進むのが正常。

ただし**前回の正常取得から 90 秒未満の場合、進行判定は見送られる**（疎通とヘルスチェックは行う）。
GitHub の cron が遅延して実行が詰まると、前の実行の直後に次が走ることがあり、その間隔では
まだ 1 ブロックも生成されていない可能性があるため。正常なノードを `chain-stalled` と
誤判定しないための措置で、通常の間隔では一度も発動しない。
本当に停止しているノードは失敗時に `lastOkAt` が更新されないので、間隔が開いて通常どおり検知される。

Peer の検査が TCP 接続確認どまりなのは、Symbol の Peer ポートが**相互 TLS 認証**であり、
Symbol PKI で署名されたクライアント証明書なしに完全なハンドシェイクが成立しないため。
「プロセスが生きて listen している」ところまでを担保範囲としている。

## セットアップ

### 1. リポジトリを Public で作成する

```bash
gh repo create node_alive_monitoring --public --source=. --push
```

Public にすると GitHub Actions の実行時間が無制限になり、完全に無料で運用できる。
ノードのホスト名は公開されるが、Symbol ノードはもともと公開情報である。
Webhook URL は Secrets に入れるため漏れない。

Private でも動くが、無料枠は月 2000 分。10 分間隔だと月 4300 回ほど実行するため枠を超える。
Private にするなら間隔を 30 分以上に広げること。

### 2. Webhook URL を取得する

- **Discord**: サーバー設定 → 連携サービス → ウェブフック → 新しいウェブフック → URL をコピー
- **Slack**: Slack App を作成 → Incoming Webhooks を有効化 → チャンネルを選んで URL をコピー

### 3. Secrets に登録する

リポジトリの Settings → Secrets and variables → Actions → New repository secret:

| 名前 | 値 |
|---|---|
| `DISCORD_WEBHOOK_URL` | Discord の Webhook URL |
| `SLACK_WEBHOOK_URL` | Slack の Webhook URL |

どちらも任意だが、**どちらか一方だけを設定することを推奨する。**

両方設定すると、片方の送信だけが失敗したときにその通知先でイベントが失われる
（全体としては「配信済み」になるため、次回に再送されない）。
1 つだけなら送信失敗 = 全滅となり、state を更新せずに終了するので、
次回の実行で同じイベントが自動的に再送される。**取りこぼしが構造的に起きない。**

どちらを選ぶかの目安: 1 人でノードを運用しているなら Discord が楽。Webhook の発行が
サーバー設定から数クリックで済み、スマホへのプッシュ通知が確実に届く。
すでに業務で Slack に常駐しているなら Slack でよい。

> **どちらも未設定の場合、ジョブは検査を一切行わずに終了コード 1 で失敗する。**
> これは意図的な挙動である。通知先が無い状態で検査を進めて state を更新すると、
> 本来送るべきだった通知が「送信済み」として消費されてしまい、後から Secret を
> 設定しても二度と送られない。だから検査自体を始める前に止める。
> この失敗は GitHub の失敗メールを発生させるが、それこそが「通知先が無い」ことを
> 知らせる最後の手段になっている。少なくとも一方の Secret は必ず登録すること。

### 4. 監視対象を設定する

`config/nodes.json` を編集する。

```json
{
  "nodes": [
    {
      "name": "my-node-01",
      "host": "node1.example.com",
      "api": { "http": 3000, "https": 3001 },
      "peer": { "port": 7900 }
    },
    {
      "name": "peer-only-node",
      "host": "node2.example.com",
      "peer": { "port": 7900 }
    }
  ]
}
```

詳細は[設定リファレンス](#設定リファレンス)を参照。

### 5. 動作確認する

Actions タブ → `node-alive-monitor` → Run workflow で手動実行する。
`monitoring-state` ブランチがまだ無い状態での実行では必ずサマリ通知が送られるので、
Discord / Slack に届くことを確認する（ブランチが既にある場合は[フォークの項](#6-フォークして使う場合)を参照）。

連続で手動実行しても問題ない。前回の正常取得から 90 秒経っていない対象は、
チェーン高の進行判定だけを自動的に見送る（疎通とヘルスチェックは通常どおり行う）。

成功すると `monitoring-state` ブランチが自動で作られる。

### 6. フォークして使う場合

このリポジトリをフォークして使うときは、上記に加えて次の 3 点を確認すること。

**(a) Actions を手動で有効化する。** GitHub はフォークされたリポジトリの scheduled workflow を
既定で無効化する。Actions タブを開いて有効化しないと、cron は一度も動かない。
しかも動いていないことは通知されないので、気づかないまま放置されやすい。

**(b) `monitoring-state` ブランチを引き継いでいたら削除する。**

```bash
git push origin --delete monitoring-state
```

フォーク時に「Copy the main branch only」のチェックを外すと、フォーク元の state ごと
コピーされる。監視対象自体はフォーク元のノードが 1 回の実行で自動的に除去されるので
問題ないが、`lastWeeklySummaryAt` だけは引き継がれるため、**初回のサマリ通知が飛ばない。**
Webhook が正しく繋がったかを確認できないまま最大 7 日間過ごすことになる。
削除すれば次の実行が「初回」として扱われ、確認用のサマリが届く。

**(c) `config/nodes.json` と Secrets を自分のものに差し替える。**
ノード定義はフォーク元のものが入っている。Secrets はフォークに引き継がれないので、
登録しないと[上記のとおり](#3-secrets-に登録する)ジョブが失敗する。

## 運用

### ノードを追加する

`config/nodes.json` の `nodes` 配列に要素を足して push するだけ。台数に上限はない。
次の cron 実行から監視が始まる。

```json
{
  "nodes": [
    { "name": "my-node-01", "host": "node1.example.com",
      "api": { "http": 3000, "https": 3001 }, "peer": { "port": 7900 } },
    { "name": "my-node-02", "host": "node2.example.com",
      "api": { "https": 3001 }, "peer": { "port": 7900 } },
    { "name": "friend-node", "host": "node3.example.com",
      "peer": { "port": 7900 } }
  ]
}
```

**1 ノード = 最大 3 つの監視対象**（http / https / peer）。上の例は計 6 対象。通知も対象ごとに飛ぶ。

実行時間はほとんど増えない。全対象を並列に検査するので、10 台でも 20 台でも
最悪ケースは約 45 秒（タイムアウト 10 秒 × 3 回試行＋待機）で頭打ちになる。

### ノードを廃止する

該当ブロックを削除して push するだけ。**`state.json` を手で触る必要はない。**
次回の実行で、その対象の state エントリも自動的に除去される（新しい state は毎回
その時の検査結果だけから組み立て直すため、設定に無いものは自然に消える）。

部分的な廃止もできる。https だけやめる場合:

```json
{ "name": "my-node-01", "host": "node1.example.com",
  "api": { "http": 3000 },
  "peer": { "port": 7900 } }
```

`my-node-01::api-https` だけが対象から外れ、残り 2 つは履歴を保ったまま監視が続く。

注意点:

- **障害中のノードを削除しても復旧通知は飛ばない。** 黙って消えるだけ。
- 「落ちているから一旦外す」場合、後で戻すと**新規ノード扱い**になる。`lastHeight` が
  リセットされ、初回はチェーン高の進行チェックがスキップされる（1 サイクル分だけ判定が甘くなる）。
- 廃止したノードは週次サマリからも消える。意図通り外れたかはそこで確認できる。

### ホスト名やポートを変える

`host` や `port` を書き換えて push する。**`name` は据え置くこと。**
そうすれば連続失敗カウントやチェーン高の履歴が切れない。

逆に、ノードを作り直して履歴もリセットしたい場合は `name` を変えればよい
（削除＋新規追加として扱われる）。

### 監視を一時停止する

Actions タブ → `node-alive-monitor` → 右上の `⋯` → Disable workflow。

**`config/nodes.json` を空にしてはいけない。** 監視対象ゼロは設定ミスとみなして
終了コード 1 で止まる設計になっており、失敗メールが届き続ける。

再開するときは Enable に戻すだけ。停止中に溜まった state はそのまま残っているので、
前回の続きから判定される。

## 設定リファレンス

### `config/nodes.json`

| フィールド | 必須 | 型 | 説明 |
|---|---|---|---|
| `nodes` | ✔ | 配列 | 監視対象ノードのリスト。1 件以上必要 |
| `nodes[].name` | ✔ | 文字列 | 識別子。**一意かつ変更しない**（state のキーに使う） |
| `nodes[].host` | ✔ | 文字列 | ホスト名または IP |
| `nodes[].api.http` | | 整数 | REST の http ポート（通常 3000） |
| `nodes[].api.https` | | 整数 | REST の https ポート（通常 3001） |
| `nodes[].peer.port` | | 整数 | Peer ポート（通常 7900） |
| `nodes[].harvesters` | | 真偽値 | `true` で、このノードに委任されている harvester の増減を通知する（既定 `false`） |

- `api` と `peer` は**少なくとも一方**が必要。書いたものだけが検査される。
- `harvesters: true` には `api` の http か https が必要（一覧を REST から取得するため）。詳しくは[harvester の増減](#harvester-の増減)。
- ポート番号は 1〜65535 の整数。
- 設定が不正な場合、監視は実行されず終了コード 1 で止まる（無言で誤動作するより止める設計）。

### http と https を両方書くべきか

両方書くと別々の監視対象になり、**https だけが落ちる（TLS 証明書の期限切れ）**パターンを
検知できる。この場合、通知に「HTTP(3000) は正常に応答しています。TLS 証明書の期限切れの
可能性があります。」という一文が自動で添えられる。Symbol ノードで最も多い静かな死に方なので、
可能なら両方書くとよい。

> **ただし、http から https へ 301 リダイレクトするノードでは `api.http` を書かないこと。**
> 前段に nginx を置いている構成でよくある。`fetch` がリダイレクトを追うため、http の監視も
> 実質 https を見ることになり、証明書切れの検知が効かなくなる。
> `curl -sI http://<host>:3000/node/health` で 301 が返るかどうかで判別できる。

### 環境変数

| 変数 | 既定値 | 説明 |
|---|---|---|
| `DISCORD_WEBHOOK_URL` | （なし） | Discord の Webhook URL |
| `SLACK_WEBHOOK_URL` | （なし） | Slack の Webhook URL |
| `CONFIG_PATH` | `config/nodes.json` | 設定ファイルのパス |
| `STATE_PATH` | `state.json` | 状態ファイルのパス |

### 実行間隔を変える

`.github/workflows/monitor.yml` の cron 式を書き換える。

```yaml
    - cron: '3,13,23,33,43,53 * * * *'   # 10分ごと（:00 を避けている）
```

`:00` ちょうどを避けて 3 分ずらしてあるのは、GitHub が「毎時 0 分付近は高負荷」と明記しているため。
`*/10` だと最も混む丸い時刻ばかりを狙うことになる。

公称の最短は 5 分だが、**指定しても そのとおりには発火しない**（[制限事項](#制限事項)参照）。
間隔を詰めても発火率が上がるとは限らず、むしろ頻度の高いスケジュールほど間引かれる傾向がある。
判定を経過時間ではなく「height が増えたか」に基づかせているため、どれだけ遅延しても誤検知にはならない。

## 通知の種類

| 種類 | 発火条件 | 色 |
|---|---|---|
| 🔴 DOWN | 2 回連続で検査に失敗したとき（1 回だけ） | 赤 |
| 🟢 復旧 | DOWN 通知済みの対象が正常に戻ったとき | 緑 |
| 📊 週次サマリ | 前回サマリから 7 日経過したとき、および初回実行時 | 青 |
| 🌾 Harvester 変化 | `harvesters: true` のノードで、委任されている harvester が増減したとき | 琥珀 |

`api.http` と `api.https` を両方設定しているノードは、2 つの独立した監視対象として扱われる。
そのため、チェーン停止のような単一の原因でも DOWN 通知が 2 件届く。これは意図した挙動である。

**週次サマリが届かなくなったら監視システム自体が止まったサイン。**
無料監視の最大の落とし穴は「監視が止まっていることに気づかない」ことなので、
これを唯一の生存信号としている。

### 失敗理由の読み方

通知の本文に出る理由は次のいずれか。

| 理由 | 意味 | 典型的な原因 |
|---|---|---|
| `unreachable` | 接続できない | プロセス停止、ファイアウォール、DNS、ホスト障害 |
| `health-down` | `/node/health` が異常を返した | API ノードまたは MongoDB の不調 |
| `chain-stalled` | チェーン高が進んでいない | 同期停止、ピア接続喪失 |
| `bad-response` | 応答が解釈できない | 別のサービスが同じポートを使っている、プロキシの誤設定 |

### harvester の増減

ノードに `"harvesters": true` を書くと、そのノードに委任されている harvester
（delegated harvesting でアンロック済みのアカウント）の増減を通知する。
委任が外れてもノードは正常に動き続けるため、死活監視だけでは気づけない。

```
🌾 Harvester 変化: my-node-01

6 → 7 件

参加: 9D4B2C01A7F3…

確認時刻: 2026-10-20T14:00:00.000Z
```

- 一覧は `/node/unlockedaccount` から取得する。https を優先し、無ければ http を使う。http と https の両方から
  取ると二重計上になるため、1 ノードにつき 1 つの URL からだけ取得する
- 公開鍵は先頭 12 文字だけを出す。アドレスへの変換はしない（外部依存が必要になるため）
- **初回は記録するだけで通知しない**（比較対象が無いため）
- **同じ実行で api 検査（http か https）が成功したときだけ比較する。** ノードが落ちている回は
  前回の一覧をそのまま残すので、障害のたびに「全員離脱」の誤報が出ることはない
- harvester の増減は障害ではないので、DOWN 判定や週次サマリの障害回数には影響しない
- 週次サマリの対象一覧の後に、ノードごとの現在件数と最終確認時刻が載る。**最終確認時刻が古いままなら、
  一覧を取得できない状態が続いている。** 一度も取得できていないノードは「未取得」と出る
- 他人のノードを監視しているだけなら書かないこと（既定は `false`）

## 状態（state）の仕組み

実行間の記憶はすべて `monitoring-state` ブランチの `state.json` に入っている。
このブランチは常に 1 コミットだけを持ち、毎回 force push で作り直される。

### 中身を見る

```bash
git fetch origin monitoring-state
git show FETCH_HEAD:state.json
```

```json
{
  "version": 1,
  "updatedAt": "2026-10-05T13:00:00.000Z",
  "lastWeeklySummaryAt": "2026-10-01T00:10:00.000Z",
  "targets": {
    "my-node-01::api-https": {
      "status": "up",
      "consecutiveFailures": 0,
      "lastHeight": "5834318",
      "lastOkAt": "2026-10-05T13:00:00.000Z",
      "downSince": null,
      "notified": false,
      "incidentsThisWeek": 0
    }
  },
  "harvesters": {
    "my-node-01": {
      "accounts": ["0A1B2C3D4E5F...", "9D4B2C01A7F3..."],
      "observedAt": "2026-10-05T13:00:00.000Z"
    }
  }
}
```

| フィールド | 意味 |
|---|---|
| `status` | `up` / `down`。2 回連続失敗で `down` |
| `consecutiveFailures` | 連続失敗回数。成功すると 0 に戻る |
| `lastHeight` | 最後に正常取得できたチェーン高。**失敗時は更新されない** |
| `lastOkAt` | 最後に正常だった時刻 |
| `downSince` | 障害が始まった時刻。継続中は最初の失敗時刻で固定される |
| `notified` | DOWN 通知を送信済みか。障害中の再通知を防ぐ |
| `incidentsThisWeek` | 週次サマリ送信時にリセットされる障害回数 |

`harvesters` のエントリは `harvesters: true` のノードにだけ作られる（該当ノードが無ければ `{}`）。`accounts` は前回確認できた
harvester の公開鍵（ソート済み）、`observedAt` はそれを確認した時刻。ノードや api が落ちていて
確認できなかった回は更新されない。設定から `harvesters` を外すと、次の実行でエントリが消える。

### リセットする

```bash
git push origin --delete monitoring-state
```

次回の実行が「初回」として扱われ、セットアップ時と同じサマリ通知が届く。
通知の配線が生きているか確かめたいときにも使える。

## トラブルシューティング

### 通知が何も来ない

1. **Actions タブでワークフローが実行されているか**を確認する。実行されていなければ
   Disable されているか、60 日の自動無効化に引っかかっている（下記参照）。
2. **Secrets が登録されているか**を確認する。未登録でもワークフローは成功するので、
   成功しているだけでは配線の証明にならない。
3. `monitoring-state` ブランチを削除して手動実行し、サマリ通知が届くか試す。

### 週次サマリが来なくなった

**監視システム自体が止まっている可能性が高い。** 設計上、これが唯一の生存信号。

最もよくある原因は、Public リポジトリの scheduled workflow が **60 日間のリポジトリ
活動なしで自動無効化**されたこと。ただし本システムは毎回 state を push するため
通常は起こらない。Actions タブに「This workflow was disabled」と出ていないか確認する。

### ワークフローが失敗する（exit 1）

ノードが落ちていても終了コードは 0。**失敗は監視システム自体の異常を意味する。**

| ログに出るメッセージ | 原因 | 対処 |
|---|---|---|
| `設定の読み込みに失敗しました` | `config/nodes.json` の JSON 構文エラー、または検証エラー | メッセージに `nodes[2]: "host" は...` のように位置が出るのでそこを直す |
| `通知先が1つも設定されていません` | `DISCORD_WEBHOOK_URL` / `SLACK_WEBHOOK_URL` のどちらも未設定 | 少なくとも一方の Secret を登録する。検査自体を行っていないので state は無事 |
| `すべての通知先への送信に失敗しました` | Webhook URL が無効、または先方の障害 | URL を再発行して Secrets を更新する。state は更新されないので、直せば次回に通知が再送される |
| `state ブランチの存在確認に失敗しました` | GitHub への一時的な到達不能 | 何もしなくてよい。state を守るためにあえて中断している。次回の実行で復帰する |

### 「異常 N 件」と出るが通知は来ない

連続失敗が 1 回だけの状態。仕様どおり（2 回連続で初めて通知）。

### https だけ落ちる

TLS 証明書の期限切れがほぼ確実。通知にもその旨が添えられているはず。
証明書を更新して REST ゲートウェイを再起動する。

### 特定のノードだけ常に `bad-response`

そのポートで Symbol REST 以外のもの（nginx のデフォルトページ、別サービス）が
応答している可能性が高い。`curl https://<host>:3001/node/health` を直接叩いて確認する。

## 制限事項

- **cron はほとんど発火しない。これが最大の制約。**
  GitHub の scheduled workflow は無料枠では best-effort で、指定した間隔どおりには動かない。
  このリポジトリでの実測値（Public 無料枠、`*/5` 指定、2026-10-16 〜 10-20 の 25 実行）:

  | 項目 | 実測 |
  |---|---|
  | 指定 | 5 分間隔（期待 約1,020 回 / 3.5日） |
  | 実際の発火 | **24 回 / 3.5日**（発火率 約 2.4%） |
  | 実行間隔の中央値 | **200 分** |
  | 最短 / 最長 | 105 分 / 458 分 |
  | 5 分以内だった回数 | **0 / 24** |

  全実行が success で cancelled も skipped もゼロだったため、`concurrency` による
  取りこぼしではなく、GitHub がスケジュール自体を発火していない。
  **数時間ダウンしたことには気づけるが、短時間のダウンは見逃す**と考えておくこと。

  分単位の検知が必要なら、外部の無料 cron サービスから `repository_dispatch` を
  叩く方式に替える必要がある（GitHub のトークンを外部に預けることになるため、
  このリポジトリでは採用していない）。
- **監視対象 40 件（ノード約 13 台）を超えると、** 大規模障害時に Discord の 1 メッセージ
  6000 文字制限に触れる可能性がある。通常は 1 メッセージ 10 件ずつに分割されるため問題ない。
- **Peer の検査は TCP 接続確認のみ。** 相互 TLS のため完全なハンドシェイク検証はしていない。
- **ファイナライズの遅延は監視していない。** ネットワーク起因の誤検知が増えるため意図的に除外。
- **自動復旧はしない。** 検知と通知のみ。
- **通知先を 2 つ設定していて片方が失敗すると、その通知先ではイベントが失われる。**
  送信は同一実行内で最大 3 回まで再試行するが、実行をまたいだ通知先ごとの配信追跡は
  していない。**これが通知先を 1 つに絞ることを推奨している理由**で、1 つなら全滅時に
  state を更新せず次回に再送されるため、取りこぼしは起きない。
  なお「全通知先成功まで state を書かない」方式はこの問題を解決しない。DOWN を受け取った
  側に復旧通知が届かなくなる（state が進まないため `notified` が立たず、復旧イベントが
  生成されない）ので、片方の取りこぼしより悪化する。完全な解は通知先ごとの配信状態を
  state に持つことだが、単一通知先では不要なため実装していない。

## 開発者向け

### ローカルでの実行

```bash
npm test                                     # テスト（ネットワークアクセスなし、174 件）
DRY_RUN=1 node src/index.js                  # 1 回だけ検査する（送信せず、state も保存しない）
DISCORD_WEBHOOK_URL=... node src/index.js    # 通知ありで 1 回検査する
```

`DRY_RUN=1` は検査を実行し、送信されるはずのイベントをログに表示するだけで、
実際には何も送信せず state も書き込まない。通知先の Secret が無い状態でも
（前述のとおり Secret 未設定は通常は即終了コード 1 になる）検査ロジックの
動作確認ができる。

`CONFIG_PATH` / `STATE_PATH` で本番のファイルを汚さずに試せる。

```bash
CONFIG_PATH=/tmp/test-nodes.json STATE_PATH=/tmp/test-state.json node src/index.js
```

### 終了コードの意味

| コード | 意味 |
|---|---|
| 0 | 正常終了。ノードが落ちていてもこちら（障害は通知で伝える） |
| 1 | 監視システム自体の異常（設定不正、全通知先への送信失敗）。GitHub から失敗メールが届く |

ノード障害でワークフローを失敗させない理由は、GitHub の失敗メールと Discord/Slack の通知が
二重に飛ぶうえ、**本物のノード障害と監視システムの故障が区別できなくなる**ため。

### ディレクトリ構成

```
.github/workflows/monitor.yml   cron 実行と state の永続化
config/nodes.json               監視対象の定義（運用時はここだけ編集する）
src/
  index.js            全体の結線と終了コードの決定
  config.js           設定の読込・検証・監視対象への展開
  state.js            state.json の読み書きと正規化
  evaluate.js         判定ロジック（純粋関数）
  harvesters.js       harvester 増減の判定（純粋関数）
  checks/retry.js     再試行と共有定数
  checks/api.js       API ノードの検査
  checks/peer.js      Peer ノードの検査
  checks/harvesters.js harvester 一覧の取得
  notify/format.js    通知先に依存しない文面
  notify/webhook.js   Webhook への POST
  notify/discord.js   Discord 用の整形
  notify/slack.js     Slack 用の整形
  notify/index.js     通知のディスパッチ
test/                 node:test（174 件）
```

`evaluate.js` は**副作用を持たない純粋関数**になっている（現在時刻すら引数で受け取る）。
このシステムのバグは「通知が来ない」という無言の形でしか現れず、本番では
「ノードが正常だから」なのか「判定が壊れているから」なのか区別できない。
だからここだけはテストで総当たりできる形に切ってある。変更するときもこの性質を壊さないこと。
